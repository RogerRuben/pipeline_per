# R6 推荐性能、页面文案与训练配置排查

日期：2026-11-03。冻结基线 `107340b`，已推送至 `codex/r6-deep-analysis`；没有合并 main 或上传交付文件。后续试验位于本地分支 `codex/r6-performance-audit`。现有开发压缩包和 EXE 尚未重新封装。

## 1. 推荐检索性能

用开发包自检训练出的实际 Optuna V3 模型、160 条虚拟历史产品、60 属性及隔离 SQLite，通过真实 HTTP 推荐接口进行前后对照。训练、模型与候选数据保持相同。

| 测量项 | 冻结源码 | 优化源码 |
| --- | --- | --- |
| 4 次非 profiler HTTP 请求 | 1.306–1.662 秒 | 0.334–0.393 秒 |
| 中位数 | 1.520 秒 | 0.360 秒 |
| 单次查询 SQLite 连接数 | 817 | 18 |
| 每次效能批量调用 | 1 次 / 160 条 | 1 次 / 160 条 |

另外，对仍在运行的 17901 实例测得 2.934、2.551、3.137 秒。用户后来打开的 54386 端口在探测时已经拒绝连接。本轮未完整复现用户描述的浏览器点击至显示超过 6 秒，不能将隔离 API 计时当成实际 EXE 和浏览器端到端的修复验收。浏览器自动化通道不可用，页面渲染时间没有完成独立测量。

定位：`Store.historical_agreements()` 已经使用效能批量接口，但参数映射、业务值还原和标签推导各自逐产品重新打开 SQLite，反复读取同样的指标定义、标签和规则。160 条产品放大为 817 次连接。隔离测试中效能批量 HTTP 仅约 0.12–0.20 秒，主要可消除开销在数据库重复读取。

已实施的源码试修：一个历史批次在短只读事务中读取一份业务元数据，关闭事务后再调用效能服务，随后在本批次复用映射和标签规则。不缓存模型预测，也不跨请求缓存业务配置；下次查询重新读取，以保留协议、规则和模型变化的即时效果。历史成交价仍参与排序，不改成预测价；批量失败后的单条隔离回退保留。

验证：5 项新增测试通过，覆盖 160 条与独立旧逐行流程结果一致、业务值映射、人工标签保留、规则更新、协议变化、批量失败与降级读取；13 项价格服务契约测试通过；原完整流水线 45 项检查通过。5 组 HTTP 结果前后逐项比较，当前页和分析列表的产品顺序、属性、价格、效能、标签及满足条件状态一致。

后续技术方案：将此优化纳入下一版冻结引擎；在同一真实 EXE、同一机器上分别测冷启动首次查询、连续筛选、分页和完整浏览器绘制。接口目标建议 160 条常规检索 P95 小于 1 秒，页面端到端另列指标，需实测确认后作为正式验收线。暂不通过跨请求结果缓存掩盖重复 I/O，也不在排序前随意截断候选。

## 2. 深度分析页面文案

当前 `index.html`、`deep.js`、`r6.js` 直接将开发验收说明、技术协议和审计来源显示在主流程，例如：模型 SHA、发布 ID、请求 ID、采样公式、MAE 置乱计算、历史参考范围的实现细节，以及“不使用旧数值替代”“不补造”等措辞。原因是 R6 功能与真实性审计要求直接落成页面文案，没有形成面向使用者的展示层。

方案：主界面只保留选产品、改属性、预测、比较、图表和导出；保留单位、真实数据/演练数据标识以及会影响用户决策的缺失、外推与未配置提示。采样公式、计算口径、模型身份和来源移至折叠的“分析说明/技术详情”；详细审计保留在导出文件和日志。使用“未配置”“暂无数据”“请填写…”等简短状态，避免向用户描述内部实现或开发约束。此次仅审计，没有改写页面。

## 3. 功能/性能/环境分类与专家评分

### 当前可以在哪里设置

- 业务分类：数据管理中心的“指标定义”中设置 `parameter_group`（指标分组），取值为功能、性能、环境；维护工作簿也有该列。深度分析从已激活发布的该字段构建分组，不在分析页编辑训练配置。
- 价格专家评分：训练前在 `input/products.xlsx` 增加“价格属性评分”工作表，列包括“英文代号”“价格重要性评分”“专家编号”，可附“属性类型”；或者填写外部 `settings/v3.json` 的 `expert.scores`，例如 `{"attr_001": 4}`。分值范围 1–5；多专家工作簿记录按已有规则取中位数；工作簿同字段覆盖 JSON。修改评分需重新训练并发布才影响模型。
- `expert.field_types` 指数值、枚举、布尔等数据类型，不能用于设置功能/性能/环境。价格专家评分也不是效能模型的权重或物理可行性规则。

### 为什么现在看不到

实际交付输入工作簿只有“成品数据”一张表，`expert.scores`、`expert.records` 和 `field_types` 均为空。训练报告中 60 个属性全部使用默认 1.0 分，`specified=false`，没有任何实际专家评分。业务发布的 60 个属性全部属于“其他”。

还存在两个具体接入缺口：

1. 通用工作簿解析器能读出“属性分组”，但 V3 复用的 `workbook_config()` 把第四个返回值分组丢弃；V3 严格 JSON 配置也不接受 `expert.attribute_groups`。因此不能简单照搬其他 AutoML 版本的分组配置。历史产品导入也没有给参数补上分类。
2. 已发布的专家条目使用 `score`、`label`，而 `r6.js` 专家评分列表读取 `importance`、`label_zh`，因此即便后端有分数，界面也会出现空值或只显示代号。这是显示字段适配问题。

后续方案：在开发包提供可填写的“属性配置”和“价格属性评分”模板；字段通过英文代号对齐。将业务分类贯通到业务发布与分析 Schema，明确与数据类型独立，校验未知字段、重复配置、分组冲突和评分范围；保留多专家原始记录、汇总值与来源。训练前检查输出“60 项属性中已分类/已评分多少项、哪些使用默认值”，避免默认值被误认成专家意见。修正 `score/label` 的显示适配，未评分项标明“未评分/使用默认值”。不改动 V3 搜索算法。

## 建议开发顺序

先完成推荐源码性能修复的 EXE/浏览器复验，再贯通属性分类与专家评分输入、检查和发布流程，最后统一精简页面文案。三项分别提交，冻结基线可独立回退。当前没有把后两项当成已经完成的功能。
