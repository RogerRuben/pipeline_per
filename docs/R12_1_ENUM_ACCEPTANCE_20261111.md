# R12.1 枚举契约与封装修复 · 2026-11-11

应用与构建代码基线：`3d50bd492d4704bd34541dd9063553de6e83dbb1`。复现基线：`2e32d13`。本轮使用虚拟资料，不代表甲方正式模型或 Win7 实机验收。

## 审阅问题的复现与修复

审阅结论成立。用 `git show 2e32d13:product/compatibility.py` 的实际转换函数，分别对 V13、V17、V15 的显式 `allowed_values` 执行转换：旧代码丢失取值表，合法业务值 A/B 被 `make_contract → encoding_gaps` 拒绝。相同输入在修复后通过。前后数据见 [reproduction.json](audit/r12_1_20261111/reproduction.json)。

原专家属性改用统一字段转换，保留 `allowed_values`、`categories` 和 `category_mapping`。运行时 HTTP Schema 同步采用这份转换结果。按英文字段 ID 读取模型 Schema 中显式声明的 `fields` 枚举元数据时，仅允许补充取值信息，不能覆盖原属性的类型、单位、必填和缺失处理规则。重复字段声明拒绝。

`encoding_gaps()`、`_accepted_codes()`、`_code_accepted()` 没有放宽。允许表之外的值、错误的业务到模型编码、缺少取值表的枚举仍拒绝。不会从业务允许值、历史样本、默认值或某个基准值推断模型的完整分类域。

## 原导出包与测试变体必须区分

实际调用附件原导出方法，生成了包含 `expert_category` 分类字段的锁 V17、泵 V13 和成品 V15 样例。附件中的 `AttributeSpec` 与原导出 Schema 本身没有完整分类取值表，原包能够独立推理，并不表示具有足够元数据可通过严格封装校验。这三个原样样例仍按预期拒绝封装，不能宣称所有原分类包已经开箱可封装。

为验证有明确取值表的正例，测试脚本另行生成**显式元数据测试变体**：在原模型对应 Schema 的 `fields` 中声明 `expert_category` 的允许值为字符串 `1`、`2`，并更新模型摘要及导出清单。这是开发者编写的合成契约样例，不是原导出器原样输出，不作为正式客户模型。该元数据表由测试作者明确声明，未从样本推断。专家算法源码 19 份保持原始 SHA 不变。

正例使用隔离的业务发布快照：原 60 字段价格业务加一个效能专用枚举字段。价格模型及其训练输入未改，也未重新训练。标准 R12B 演示运行包仍使用原来的 60 字段业务与两数值属性泵模型，枚举回归资料用于开发复现，不能直接套到缺少该字段的产品中。

V15 原导出器还要求 `product_ui.html`，但附件系统目录缺少该文件。生成样例时，在隔离导出目录中用原模块的 HTML 常量恢复这个导出附件，不修改原算法。修复本软件的必需文件检查：Python 源文件继续逐份核对内置算法哈希；HTML 等非执行附件核对导出清单。此前 V15 会因为 HTML 不计入 Python 文件集合而被误拒。
